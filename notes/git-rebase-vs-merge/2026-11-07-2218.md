# Git Rebase vs Merge

**Merge** preserves history exactly as it happened. It creates a new "merge commit" tying two branches together, keeping the original commit hashes and chronological order intact. This is safe for shared/public branches because it never rewrites history, but it can clutter logs with criss-crossing lines.

**Rebase** rewrites history for a linear narrative. It takes your local commits, temporarily removes them, updates your branch to the target's tip, then replays your commits on top one by one. This eliminates the merge commit and yields a straight line in `git log`, but it changes commit hashes. **Never rebase commits pushed to a shared remote**—it forces collaborators to deal with divergent histories.

Use **merge** for integrating long-lived features or shared branches (e.g., `main` ← `feature`). Use **rebase** locally to clean up "WIP" commits or update a feature branch against `main` before opening a PR.

```bash
# Merge approach (preserves topology)
git checkout main
git merge feature-xyz  # Creates merge commit

# Rebase approach (linear history)
git checkout feature-xyz
git rebase main        # Replays feature commits onto main
```
